# Whole-book reconciliation

Governing source: [Righting Software](<../references/Righting Software.pdf>). Review scope and limits are recorded in [source review](source-review.md).

| Finding | Framework resolution | Source |
| --- | --- | --- |
| The Method contains system and project design | Keep both accountable to the Solution Architect; PM manages execution | Chapters 1, 7 |
| Business understanding precedes decomposition | Add vision, objectives, mission, glossary, and bidirectional traceability | Chapter 5 |
| Functional discovery differs from architectural decomposition | Preserve requirements analysis; reject functional architecture | Chapters 2, 4 |
| Closed layers have explicit interaction exceptions | Preserve Manager-to-Engine and Utility permissions; classify requests versus events | Chapters 3, 5 |
| Example technologies are contextual | Do not mandate TradeMe's bus, workflow, or Abstract Manager | Chapter 5 |
| Project design is a dependency-driven engineering process | Record the 21 activities, per-option work, and SDP decision | Chapters 11–14 |
| Compression changes the work | Require simulator work and subsequent real-service integration and retesting | Chapters 9, 11 |
| Decompression adds float | Preserve estimates and staffing | Chapter 10 |
| Risk definitions and thresholds vary | Identify model and conditions; preserve undefined cases and outlier handling | Chapters 10, 12, 13 |
| Printed scaling ratio contradicts companion | Use companion C/R under explicit owner resolution; retain discrepancy | pp. 310–311 |
| Detailed design can be delegated | App Architect owns detail within system bounds; SA review precedes handoff | pp. 374–377 |
| QA differs from testing | Dedicated QA reports to SA under owner assignment | Chapter 14 |
| Lifecycle contains parallel paths and feedback | Preserve STP branch, review retries, developer test client, and integration testing | Appendix A |
| SRS and STP are service-level artifacts | Correct their expansions and preserve their scope | Appendix A |
| Progress and effort use different weights | Preserve binary phase exits, duration-weighted progress, and cost-based effort | Appendix A |
| Contract metrics cannot validate design | Preserve semantic evaluation and absolute twenty-operation rejection | Appendix B |
| Appendix C distinguishes directives and guidelines | Retain all 115 identifiers and classifications | Appendix C |
| Agent costs need an explicit basis | Add owner-selected token accounting without changing schedule units | Owner decision |
| Source rules need compact consumption | Add Standard Technical English and JSON records with context and authority | Owner request |

The [Standard Technical English extraction](../standards/rules.ste.md) is a paraphrase and navigation aid. It does not replace the book or grant workers authority to change constraints. Enforcement boundaries describe required protections; those protections have not been deployed. Application technology, calendar, identities, and integration mechanisms remain decisions rather than implied defaults.
